# Architecture

How the extension fits together. For build commands and the rules agents must follow, see [AGENTS.md](./AGENTS.md). Class-level behaviour is documented by the code and its tests; this file covers the shape and the reasons behind it.

## Wiring

`McpScannerExtension` (Burp's `BurpExtension`) builds the object graph through the `*Wiring` classes and `ExtensionFoundation`: settings, the event log, the client manager, the check registry, the scan launcher, the local proxy and the Swing tab. `BurpEdition` reads Burp's edition at load. `ExtensionFoundation`, `ConnectionWiring`, `OAuthWiring`, `IdentityWiring` and `RequestBuildingWiring` are built in every edition; only in Burp Suite Professional does `ProfessionalFeatures` build the scan, Collaborator, engine, Check access, Collect IDs and compared-user discovery wiring, and the entry point add the Professional UI. `ProfessionalOnlyWiringTest` enforces the split. `ConnectionWiring` builds **one** upstream transport (`SharedUpstreamTransport`) that Connect, discovery and the proxy all share, and `ShutdownHooks` closes executors and pollers on unload.

**Settings.** `config/ExtensionConfigStore` reads every setting from the project (`extensionData()`), else the built-in default, through `LayeredSettings`; writes go to the project only. A project with no extension keys at all is new: on load it is seeded once from the user defaults (`preferences()`) and marked `mcp.defaults.seeded`, so later "Save as my defaults" never changes a project that already exists, and a project saved by an older release (which stores only changed keys) loads exactly as before. `SettingKey` declares each key or key family as `USER_DEFAULT` or `PROJECT_ONLY`; an undeclared key is treated as project-only, an exact declaration beats a family, and a key may name risky values (redirect mode `ALWAYS`) that are never saved or read as a user default. The OAuth registration mode is project-only because Pre-registered and CIMD need the project-only client ID or metadata URL. Targets, users, tool choices and risky opt-ins are project-only and are never read from or written to preferences (`SettingKeyTest`, `UserDefaultSettingsTest`). "Save as my defaults" copies the project's user-default values to preferences; "Reset my defaults" clears preferences and leaves the current project as it is.

## Connecting to a server

`McpClientManager` coordinates `McpDiscoveryClient` (catalog listing and mapping) and `McpScannerSession` (protocol bring-up and the live session scanning uses). Three transports:

- **Modern HTTP**: `server/discover`, versioned request metadata and routing headers, no session id.
- **Initialize-based Streamable HTTP**: `initialize` + `notifications/initialized`, version negotiation, `Mcp-Session-Id`.
- **Legacy SSE**: open the event stream, read the `endpoint` event for the message URL.

**Networking.** MCP connection traffic goes through Burp's own HTTP stack while "Send requests through Burp" is on (the default), so Burp's client TLS certificates, upstream proxy and TLS settings apply; otherwise it goes through the JDK client. SSE always uses the JDK client, because Burp cannot read an open event stream. Burp also refuses `text/event-stream` replies to extensions; the Burp transport detects that (`mcp/BurpStreamingRefusal`) and either falls back to the JDK client for that route or offers to turn the setting off. Burp reports every streamed reply as a refusal (first, repeated, concurrent or on a reused connection) and returns an empty reply only when the server sent nothing before closing, so an empty reply is never taken for a stream and a call that may write is never resent after one. A check's `StreamingFallback` covers probes that do not go through the proxy and tells `StreamingRefusalWatch` (`OutsideBurpSends.streamRefused`) when Burp refused one; a check opening its own stream outside Burp is not a refusal.

**Requests that cannot go through Burp (BApp Store networking exception).** Burp refuses streamed (`text/event-stream`) replies to extensions, so three kinds of send go outside Burp's HTTP stack even while "Send requests through Burp" is on: the JDK SSE client that holds the legacy SSE event stream open, the JDK and raw-socket fallbacks that recover a probe Burp refused (`StreamingFallback`, reported through `OutsideBurpSends`), and stream probes that must read an open event stream. Burp's upstream proxy and TLS settings do not apply to these sends. This is an accepted, unavoidable exception (decided 2026-11-18): there is no workaround while Burp withholds streamed replies from extensions. The setting governs the MCP connection's traffic; OAuth sign-in and metadata requests, Check access, Collect IDs and checks always go through Burp. The OAuth auth probe's unauthenticated event-stream GET (`auth/oauth/discovery`) follows it through `NetworkingSelectedChallengeSender`: through Burp when the setting is on, where real Burp refuses the stream as soon as its headers arrive (measured by `BurpAuthProbeCanaryTest` in `burpCanary`: about 5 ms, read as no auth needed) and its response-timeout empty reply counts as no answer; through the JDK client when it is off.

**Connection reuse.** Burp keeps an extension's HTTP/1 connection alive only when a send names a connection id, and otherwise waits for the server to close after each reply. `ConnectionReusingHttp` names one for origins known to speak HTTP/1.x. Burp keeps a pool of sockets per connection id, so `KeptAliveConnections` gives each send in flight its own id: an id is taken for one send and put back only when that send was answered. A disconnect starts a new generation of ids, so a send still in flight across it never puts its old id back. Servers close idle kept-alive connections (gunicorn after 2 s, Node and uvicorn after 5 s), and Burp then answers the next send on that id with an empty reply, sometimes after writing the request onto the half-closed socket, so an id idle for more than a second since its last reply (`KeptAliveConnections.IDLE_LIMIT`) is never used again; `BurpIdleClosedConnectionCanaryTest` in `burpCanary` guards it through the extension's `api.http()` path. The limit is checked when the id is taken, and Montoya has no hook to check it again just before the wire: an `HttpHandler` sees the request after Burp's scan queue but cannot change its connection id, and must not synthesise a reply. So a check send through the scanner's Http that waits in the scan queue (resource-pool throttling, or Burp pacing a host whose replies carry `RateLimit-*` headers) longer than the server's keep-alive gets an empty reply. `ConnectionReuse` then resends it once on a fresh `Connection: close` connection, but only reads and handshakes, never writes (`ResendableBurpRequests`, built in `ConnectionWiring`, asks `mcp/ResendableRequests`, which alone decides: a request with a body by its JSON-RPC method, a body-less request only for GET, HEAD or OPTIONS; the scanner session's stale-connection resend, `client/StaleConnectionResendingTransport`, asks the same, so a body-less DELETE is never resent). The resend uses `Connection: close` rather than a new id because the origin falls back to fresh connections after any unanswered reused send anyway, and a new id would leave one more socket pooled in Burp. A write that hit a closed connection is not resent: its probe gets no answer. The same canary also sends a read held longer than the server's keep-alive between taking its id and reaching Burp (the harness's `ScanQueuedHttp` stands in for the scan queue) and fails unless it is answered. A retired id's socket stays open in Burp for as long as the server keeps it (12 retired ids against a server with a 75 s keep-alive left 12 established sockets in Burp 35 s later), so `KeptAliveConnections` opens at most `MAX_CONNECTIONS_PER_ORIGIN` (64) ids per origin until the next connect; once they are used up, a send that finds no fresh id goes on a fresh `Connection: close` connection. Burp also keeps a separate socket pool per send path under the same id: one id used alternately through `api.http()` and a check's audit `Http` went over two sockets, while two audit `Http` objects from `doCheck` calls in two separate audits, used one after the other, shared one socket. So `KeptAliveConnections` keeps its idle ids per send path (`SendPath`: EXTENSION for `api.http()`, SCAN for every audit `Http`, wrapped by `ConnectionReusingHttp.aroundScanSends` beneath the scan-queue bypass so a send moved off the queue takes its id from the `api.http()` pool), and an id is never sent through both; the cap of 64 ids counts both paths together. Before, an id kept fresh by `api.http()` traffic could reach the scanner's socket for it after the server had closed it, and a write's answer was lost. `BurpAuditPathWriteCanaryTest` in `burpCanary` guards it: a write from a check registered through the production `RequestCheckAdapter`, over Burp's real audit `Http`, after 3 s of `api.http()` traffic on the same origin must be answered (with one shared pool it went unanswered), and `HostCheckAdapterTest` pins the adapter's wrapping order.

**OAuth check sends leave the scan queue.** Burp paces every scanner request to a host by the `RateLimit-*` headers of any reply its scan queue sees from that host. The TypeScript SDK's `mcpAuthRouter` answers `/register` and `/authorize` with `RateLimit-Policy: 20;w=3600`, so OAuth probes sent through the scan's Http made Burp send about one request every three minutes to that host for the rest of the scan (seen in a thread dump of Burp's queue worker; the second registration never reached the wire). Requests to the authorization server therefore go through `api.http()`, which Burp does not pace: `checks/shared/oauth/OAuthHttp` (and the refresh check's token requests) mark each send with `http/OutsideScanQueue`, and the `http/ScanQueueBypass` that `ScanningWiring` gives the check adapters wraps the Http Burp's scanner hands a check and routes a marked send to the extension's own `api.http()` sender (`ConnectionWiring.burpHttp`, the one OAuth sign-in uses), beneath the adapter's connection-reuse, counting, Retry-After, evidence-retention and telemetry wrappers, so those still see it. The extension's own scan engine already sends through that sender and counts every request for the Scans tab, so it hands checks an Http marked `ScanQueueBypass.alreadyOffScanQueue` that the router leaves alone. Burp's upstream proxy and TLS settings still apply. The extension stays polite to the authorization server on its own: a 429 stops the check's OAuth probing (`OAuthHttp`, `RateLimitCoolDown`). MCP requests a check sends with a token it obtained stay on the scan queue.

The MCP protocol, OAuth and connection-core logic (framing, negotiation, response validation, SSE semantics) lives in the project's own core libraries, Java 17 Gradle subprojects in `core/` with no third-party dependencies: `mcp-protocol-core`, `mcp-oauth-core` and `mcp-connection-core` (which depends on the other two), in the packages `com.mcpscanner.core.protocol`, `com.mcpscanner.core.oauth` and `com.mcpscanner.core.connection`. `core/core-module.gradle` builds each as a reproducible JAR plus sources JAR (other projects consume these) and runs every test-source class with a `main` method as a self-checking test (`selfTest_*` tasks, wired into `test`). They are the only implementation of it: generated scan requests are framed through `McpScannerSession.operation`, and catalog checks may call the protocol core directly.

## The local proxy

`proxy/SseProxyServer` is a loopback NanoHTTPD server that sits between Burp's scanner and the target. `McpHttpHandler` swaps the service of every scanner request so it reaches the proxy, which then:

- terminates SSE streams and hands Burp a bounded HTTP response (Burp's scanner cannot consume an open event stream, so the proxy is mandatory for SSE);
- rewrites JSON-RPC ids so concurrent scan requests stay distinct, and restores the scanner's id on the reply;
- injects the primary user's credentials and live `Mcp-Session-Id`, re-handshaking on session-not-found (but forwards a fuzzed, unknown session id unchanged);
- re-frames every forwarded body (routing headers and `Mcp-Param-*` headers derived from the body), so a check that swaps a body only needs `withBody`;
- relays upstream status and headers faithfully, and relays HTTP errors on handshakes instead of turning them into 502s;
- forwards a scanned `initialize` (Burp's or a check's fuzzed copy of the generated one) in a session or SSE stream of its own, never on the live session, because a server that accepts a second `initialize` resets the session and every later request on it fails (`HttpForwarding`, `IsolatedHttpForwarder.forwardInitialize`, `SseForwarding`).

Scanner-internal **sentinel headers** (`ScannerSentinels`, `X-Mcp-Scanner-*`) steer routing: direct delivery (bypass the proxy), strip credentials, run as another identity, keep the live session. They are stripped before anything goes upstream. The proxy refuses browser-originated requests (`Origin` / `Sec-Fetch-*`) that do not carry its per-load routing key, so a DNS-rebinding page cannot use the loopback port.

**Why not intercept in `HttpHandler`?** Synthesising a response with `RequestToBeSentAction.continueWith(...)` fires too late in Burp's scanner pipeline; the request is already on the wire. The only exception is `Http1LoopbackRelay`, which uses `spoof` for HTTP/2 and non-Scanner requests because Burp fixes the HTTP mode before the handler runs.

**Issue evidence shows the target's exchange, not the proxy hop.** Every evidence exchange is an `http/evidence/WireRecord`: Burp's own returned exchange, a JDK send rendered exactly as the JDK HTTP/1.1 client writes it (its Host, Content-Length and User-Agent, sorted headers, joined cookies), or the bytes a raw socket wrote and read (`SocketTap`); a legacy HTTP+SSE exchange is two items, produced only by `http/evidence/LegacySseExchange`: the POST with the server's own reply to it (usually `202 Accepted`), then the GET that opened the event stream with the stream's real head and the raw bytes of the event that answered the POST. Each forward records what was actually sent upstream (`UpstreamCaptures`, `RecordingTransport`) into a bounded `UpstreamExchangeStore`, and tags the reply with `X-Mcp-Scanner-Exchange`. The store evicts oldest first, and a scan sends far more probes than it holds, so two kinds of evidence are kept from eviction: the scan launcher remembers each request it launches (`mcp/LaunchedBases`, through `BaseRememberingRenderer`), and the first forward of each launched body, which is the base Burp or the engine fetched and hands every check, is pinned in a small least-recently-used set (`PinnedBases`); and `CollaboratorWatch` keeps the probes a late issue will attach already resolved to their wire records (`http/WireResolvingCopies`), so an interaction that arrives minutes later never needs the live store; a legacy SSE probe resolves to two items while a check holds one per probe, so the watch keeps the proxied exchange and the store keeps temp-file copies of its two items in a separate least-recently-used map of 10,000 entries (`UpstreamExchanges.keepResolved`), consulted after the live exchanges. `http/UpstreamEvidence` swaps tagged proxy exchanges in an issue for the stored upstream ones, carrying highlight markers and the truncation note over; when one proxied exchange becomes two legacy SSE items, its request markers go on the POST and its response markers on the event, and the issue detail gains one sentence (`http/SplitExchangeNote`) saying how each exchange described is shown. Both issue paths (the check adapter and Check access) then pass every issue through `http/evidence/ReportedEvidence`, which strips any `X-Mcp-Scanner-*` sentinel left by a missed swap (credentials stay) and adds one sentence to the detail when the scanner's size cap truncated a body. `architecture/EvidenceFidelityTest` keeps responses from being built or altered outside `http/evidence`.

## Checks

Every check is one of three kinds, decided by its interface:

| Kind | Interface | Called |
|---|---|---|
| `INSERTION_POINT` | `InsertionPointCheck` | once per fuzzed field |
| `REQUEST` | `RequestCheck` | once per scanned request |
| `HOST` | `HostCheck` / `RetryingHostCheck` | once per host trial per connection, until a trial settles |

HOST checks register with Burp as per-request: Burp's own per-host invocation would stop retries, so `HostAudits` is the only host dedup. A trial settles, is released unprobed, or is released as inconclusive or as an unsuitable seed, each with a retry limit.

Packages under `checks/`:

- `api` — the kernel: descriptors, kinds, `CheckFactory` (the `ServiceLoader` SPI), `CheckServices`, `CheckCatalog`, `CheckRunner`, `HostAudits`, `CheckLog`. `api/crossidentity` is the probe kit shared by Check access and session binding.
- `registry` — the Montoya side: `McpCheckAdapter` and one adapter per kind, owning toggles, lifecycle logging and the evidence swap. It never names a concrete check.
- `issue` — issue rendering shared by checks.
- `shared` — toolkits: JSON-RPC parsing (`jsonrpc`), probe sessions (`session`), anonymous probing (`probe`, `auth`), event-stream probes (`stream`), Collaborator (`collaborator`), OAuth (`oauth`), field naming. Issue evidence is always the raw exchange; nothing redacts it. A probe sent outside Burp returns the raw wire reply (SSE and chunk framing kept), so checks read and compare reply bodies through `jsonrpc/ReplyBody` and `McpReply`, never `bodyToString()`.
- `catalog/<check>` — one package per check.

**Streamed replies.** Burp discards a check invocation's whole result once any send met a streaming refusal, even one the check recovered from. The adapter detects this and files the issues itself. `StreamingFallback` recovers probes outside Burp (JDK client, or a raw socket for foreign `Host` headers), and every such send is reported through `http/OutsideBurpSends` so request counts stay right.

**Collaborator.** No check thread waits for interactions. `CollaboratorWatch` is one shared poller per load; a check registers its payloads and returns, and findings arrive later through `lateIssues()`, which routes them through the same adapter and site-map consolidation as returned issues.

**Rate limits.** Fuzzing checks stop probing after the first HTTP 429, and also once any answer says the server's rate limit has no requests left for at least 10 s (`RateLimit-Remaining: 0` with `RateLimit-Reset` of 10 s or more, or `r=0` with `t` / `remaining=0` with `reset` of 10 s or more in the structured `RateLimit` field; a shorter or epoch-sized reset does not count). `mcp/RateLimitStop` alone decides this, for the shared probe channel (`ProbeChannel`) and for `RateLimitedProbing`. The proxy still relays the server's `RateLimit-*` headers and Burp keeps pacing the scan by them; but that pacing kept probes off the 429 itself and the 429s that did come back were waited out and resent, so checks swept on at the server's quota (telnyx-mcp 7.3.0: 60 failed requests a minute, express-rate-limit sending `RateLimit-Remaining: 0` on every reply once spent; 30+ min in `cveTargetsBurp`). A spent quota never stops confirming a hit already seen, because the hit's own reply can carry it: `RateLimitedProbing` hands a check `probes()`, withheld after a 429 or a spent quota, and `confirmations()`, withheld only after a 429, and `ProbeChannel.barsConfirmation` is true only for a 429 or a spent send budget. `Retry-After` resends, whether a reply counts as an answer, and Check access's stop still look at the 429 alone. Every check's `Http` honours a short `Retry-After` once.

## Scan generation

- `scan/request` — the request generator: one builder per `RequestFamily` (tool calls, resource and template reads, prompts, list requests, notifications, lifecycle requests, OAuth client registration), filtered by the user's toggles, the server's capabilities and the negotiated version.
- `scan/field` — the field generator: every JSON leaf under `params` becomes an insertion point, plus non-transport request headers and resource-template variables. Burp builds with native JSON-RPC insertion points get those argument leaves left to Burp, so fields are not fuzzed twice. The `params._meta` envelope is the same server code on every request, so a launched scan offers it on one base request per server (`MetaEnvelopeCarriers` picks a listing or lifecycle request first, never a notification while a request carries it) and holds the rest as passengers in `MetaEnvelopeRegistry` until the scan ends; the Requests option "Fuzz request metadata (_meta) on every request" turns that off, and a request no scan holds keeps its `_meta` fields. On the proxy's session path the server never sees the scanner's URL query, JSON-RPC id or transport headers: the proxy sends its own (`ReservedHeaderPolicy.reachesServerOverSession`). So the check adapter skips, with a logged reason, any insertion point whose payload changes only those while both the base and the altered request still take that path (`proxy/ProxyDroppedChanges`, asked through `ScannedLeaves`): Burp's native `id` and URL query points. A payload that changes the route (the URL path, a session id the scanner did not issue, a sentinel) is still fuzzed, because it reaches the server another way. Skipped probes reached the server as the unchanged call, which on a slow tool cost a full call each for nothing. Burp's built-in checks still fuzz those points (Montoya cannot remove Burp's native insertion points), so with built-in checks on, a slow tool still costs a full call per built-in probe of them (cve-targets/README.md, Burp mode limits). For scanner-launched requests the proxy derives `Mcp-Method`, `Mcp-Name` and `MCP-Protocol-Version` from the body and session, but a scanner request's own value reaches the server when it is a payload (`proxy/OperationHeaderFraming`). Every request the scanner renders (`McpHttpRequestFactory`) records the values it framed in the `X-Mcp-Scanner-Framed-Operation` sentinel (`mcp/FramedOperation`), which Burp copies into every probe and the proxy strips: a header equal to its recorded value is the base's (left stale by a body payload, or unchanged) and is derived again, any other value is sent as is. Items handed to Burp's tools (Repeater, Intruder, Organizer, Comparer, Decoder) leave without the sentinel (`ui/sendto/MontoyaSendToDestinations`), so a project reopened without the extension never resends it to a target or shows it in a copied command; like any request without the sentinel (older history, a request built by hand), their operation headers reach the server exactly as typed, because Repeater is a raw tool and a header the user edited is the point of the request; the proxy fills in only an operation header such a request lacks. So a scan or Intruder attack launched on such a request (rather than on one the extension rendered) sends its base's operation headers unchanged, even where a body payload has made them stale. A request whose sentinel is present but unreadable (Burp fuzzed it) has its headers derived. `proxy/ProxyDroppedChanges` counts these headers as reaching the server on every request. Every path that bypasses the proxy (`McpHttpHandler`) strips all of `ScannerSentinels.STRIPPED_BEFORE_UPSTREAM`, so the sentinel never reaches a target. `Mcp-Param-*` headers are always derived from the body.
- `McpScanLauncher` renders each request once and sends the batch to the chosen `ScanMode`: the extension's own engine (default) or a Burp audit with the built-in checks too.
- `OwnedArguments` fills a tool call's arguments from the primary user's owned values, so Scan and Check access send the same owner request.

## The extension's scan engine

Montoya cannot start an audit without Burp's built-in checks, so `engine/McpScanEngine` runs the same `McpCheckAdapter` instances itself on a resizable worker pool: per-insertion-point checks once per field, request and host checks once per request. Issues are consolidated against the live site map the way Burp does. Its probes appear in Burp as tool "Extensions". The Scans tab shows its history.

## Users and Check access

- `identity` — every user (one **primary user** that Connect and Scan run as, plus compared users), their in-memory credentials and owned values. Credentials are bound to the endpoint's origin and cleared when it changes.
- `access/mining` — "Collect IDs": calls read-only tools as each user to learn which object ids are theirs. Write tools run only when opted in and confirmed. Every user's calls in a pass run concurrently on as many workers as extension scans use (`mcp.scan.engine_workers`); each pass waits for the previous one because it feeds that pass's IDs. By default a user is sent whatever their passes need; `mcp.mining.requests_per_user` sets an optional ceiling.
- `access/comparison` — Check access: per item, the owner's request, a replay as each compared user and as the two synthetic principals (`api/crossidentity/SyntheticPrincipals`: No credential, and a Fake token the server never issued), with escalation probes where they can matter. Operation-level findings are filed as Burp issues; object-level ones only when a hand-entered private marker proves them, otherwise they stay on the Access grid as possible leaks. Read items run concurrently on a shared worker pool, capped at 8 requests in flight per run (`InFlightLimit`); write items run after every read, one at a time, least to most harmful.
- `access/listing` — the synthetic principals' `tools/list` also feeds the catalog union (`CatalogUnion`), so a tool only they list gets a row; `ToolListingAudit` files "fake token lists tools the primary user does not list" (High) and "unauthenticated principal lists more tools than a real user" (Medium), each raised to High / Certain when one of the extra tools answers a call.

## Signed-in consent (Professional)

The OAuth consent check's signed-in trial reads the user's session through the `checks/api/SignedInConsent` port on `CheckServices` (default `SignedInConsent.OPTED_OUT`). Only `ProfessionalFeatures` builds the Burp side, through `SignedInConsentWiring`, and passes it to `ScanningWiring`; the `signedin` package is a Professional-only part in `ProfessionalOnlyWiringTest`, and neither `auth/` nor `checks/` depends on it.

With cookies, the trial registers one probe client per `SignedInProbe` (fresh name, the scanner client's name, its redirect host, its `client_id` prefix, a broader scope), redeems a code issued without consent once to prove access, and reports only the most specific shortcut; every token is revoked and every client deleted.

- `config/SignedInConsentSetting` — the opt-in, off by default, saved only in the project (`mcp.oauth.consent.signed_in`); the Checks section shows it as "Test OAuth consent with my sign-in".
- `signedin/CookieJarSessions` — the unexpired cookies Burp's cookie jar holds for the authorization server's host, each with its path, so `checks/shared/oauth/SameOriginRedirects` sends each hop only the cookies whose path covers it. Montoya exposes no host-only flag, and Burp stores both a host-only cookie of `example.com` and a `Domain=example.com` (or `.example.com`) cookie as bare `example.com` (checked in headless Burp 2026.x), so a bare parent-domain cookie counts only when `ProxyHistoryCookieOrigins` finds that the latest `Set-Cookie` in Proxy history that wrote that jar entry (same name, value, domain and path) carried a `Domain` attribute, so a value written outside Proxy or no longer in its history is not sent; one set by an extension with a leading dot always counts. Never logged or persisted.
- `signedin/ConnectSignIns` — the Connect OAuth sign-in, learnt through `auth/oauth/SignInListener` on the Connect flow only (not the compared-user sign-in flow); it becomes current when Connect succeeds and is forgotten on Disconnect.
- `signedin/BrowserConsentFallback` — also told of the Connect sign-in (`SignInListener`): when opted in, on a daemon worker, registers a probe client by anonymous DCR (same client name as the scanner's) with a loopback `CallbackListener` on a fresh path, opens its authorization URL in the OS browser through the validated `BrowserLauncher`, waits 2 s for a code it never redeems, then repeats with a fresh name only if a code arrived; probe clients are deleted (RFC 7592) on every path.
- `signedin/BrowserConsentObservations` — what the Connect-time browser probe saw, cleared on Disconnect.
- `signedin/BurpSignedInConsent` — the port: offers nothing unless the project opted in.

## Running checks outside Burp

`CheckRunner` mirrors Burp's dispatch so a check can run against a live target without Burp:

```java
MontoyaTestFactory.install();
Http http = new RecordingRealHttp();
McpCheck check = CheckCatalog.discover(services).find("<check-id>").orElseThrow();
List<AuditIssue> issues = new CheckRunner(http, new McpInsertionPointProvider()::provideInsertionPoints)
        .run(check, baseRequests);
```

`CheckServices.standalone()` supplies no-auth, no-Collaborator defaults. A check that reports through Collaborator needs `services.reportingLateIssues(watch, new SettlingLateIssues(watch))` and a `CheckRunner` given that settlement.

## Test infrastructure

- **Request budgets** (`performance/RequestBudgets`, part of `build`): Connect, every catalog check and a Check access item each have a request budget against in-process fixtures; exceeding one fails with a breakdown.
- **CVE target harness** (`cve-targets/`, `src/test/java/com/mcpscanner/cvetargets`): real vulnerable/fixed Docker pairs, run directly through `CheckRunner` or through headless Burp Pro using the loopback-only `automation` API (`/scan-all`, `/audit`, `/check-access`, and `/signed-in-session`, which puts cookies in Burp's cookie jar and opts the project in; `/scan-all` can carry the same session plus a scanner client, delivered to `signedin/ConnectSignIns` as a sign-in at that Connect), which lives in `src/automation/java` and ships only in the harness JAR. See [cve-targets/README.md](./cve-targets/README.md).
- **Burp canary** (`burpCanary`): headless Burp against a local keep-alive server, failing if connection reuse is bypassed or sends serialise.
- **Slow link** (`slowLinkTest`): runs Connect, Check access and a scan through a relay that adds latency per hop, failing any operation slower than its request count and declared concurrency allow, or any traffic that bypassed the relay.
- **mTLS**: `MutualTlsConnectTest` in Java; `test-server/` serves HTTPS with client certificates for a manual Burp check.
